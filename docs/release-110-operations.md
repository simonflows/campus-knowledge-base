# Обновление Канона до 1.1.0

Попытка `f110n27a` переключает принятую 1.0.0 (`f100n26b`, ревизия `c1405c6987bd22b0c740c935c0af28625dc79fa7`, пин `29-release-100-update.conf`) на проверенный образ 1.1.0. Запускайте её в согласованное окно обслуживания. Контракт 11 рабочих таблиц и механизм копирования остаются прежними. Изолированное восстановление создаёт таблицы только в префиксе `qa095-110-f110n27a-old-`. [Приёмка исходной версии](release-1.0.0-acceptance.md)

## Подготовка образа

1. Возьмите точную новую ревизию `main`, успешный запуск `CI` для её `push` и ID артефакта `canon-release-image`. `Quality gate` должен пройти для той же ревизии. На доверенной машине оператора скачайте ZIP через настроенный `gh` и проверьте его следующими командами. `$revision`, `$ciRunId` и `$artifactId` берутся из выпускаемой ревизии и её запуска.

   ```powershell
   python -c "import subprocess, sys; f = open(sys.argv[2], 'xb'); subprocess.run(['gh', 'api', '--hostname', 'github.com', 'repos/simonflows/campus-knowledge-base/actions/artifacts/' + sys.argv[1] + '/zip'], stdout=f, stderr=subprocess.PIPE, timeout=600, check=True)" $artifactId candidate.zip
   python -B deploy/ci_image_load_110.py verify $revision $ciRunId candidate.zip candidate-verified
   ```

2. Зафиксируйте точные ревизию, ID запуска и артефакта, SHA-256 ZIP и ID образа из `ci-provenance.json`. Перенесите эту квитанцию и `canon-release-source.tar.gz` в новый каталог `/var/lib/canon/build110-<revision>` на ВМ. Родитель и каталог принадлежат `root:root`, режим каталога `0700`, файлов `0600`. ZIP и учётные данные `gh` остаются на машине оператора.
3. Передайте из той же проверенной ревизии `deploy/ci_image_load_110.py` и `deploy/ci_image_load_100.py` в один каталог инструментов на ВМ, доступный на запись только root. Сверьте контрольные суммы этих файлов. Через доверенный двоичный канал передайте `canon-release-image.tar.gz` на стандартный ввод загрузчика от root. Переменная `revision` на ВМ содержит ту же точную ревизию.

   ```sh
   /usr/bin/python3 -B /path/to/ci_image_load_110.py load "$revision"
   ```

4. Загрузчик проверяет пакет 1.1.0 в архиве исходников, полный архив и дерево, размер и SHA-256 потока, неизменяемый ID и OCI-метки образа, а также возможность создать из него остановленный контейнер. Сверьте ID загруженного образа с записанным ID, цепочку слоёв из `ci-image-receipt.json` с нативным snapshot containerd в состоянии `Committed`, оставшееся место и inode. Сохраните результат вместе с доказательствами выпуска.

## Переключение

Проверьте, что работает `f100n26b`, `/api/ready` возвращает `ready`, каталог `/var/lib/canon/release110-f110n27a` и пин 30 свободны. Сохраните установленное дерево `build100-<revision>` и маркеры предыдущих выпусков. Скрипт проверяет принятое состояние `f100n26b`, включая оба условия пина 29, точные команды systemd, рабочий runtime и обе TTL-таблицы. Перед началом он повторно сверяет полный исходный архив кандидата, рабочий Compose, версию пакета 1.1.0 и совпадение схемы и скриптов копирования с 1.0.0.

Запустите из проверенного дерева. Переменная `image` содержит полный ID `sha256:…` из квитанции загрузчика для `revision`.

```sh
/usr/bin/python3 -B "/var/lib/canon/build110-$revision/source/deploy/release-110-update.py" "$revision" "$image" f110n27a
```

1. Скрипт останавливает рабочий экземпляр и публикует закрытый `30-release-110.conf`. Он делает свежий снимок всех 11 таблиц, проверяет его без сети и восстанавливает копию в изолированный префикс. Результаты сохраняются в `/var/lib/canon/release110-f110n27a`.
2. Кандидат запускается с запрещённой записью и политикой перезапуска `no`. Скрипт проверяет readiness и версию на localhost и HTTPS, ответ `503` на GET и HEAD OAuth callback без cookie и редиректа, а также TTL. Во втором снимке все девять обычных таблиц совпадают побайтово по хешам. Из двух TTL-таблиц могут исчезнуть только строки, чей срок истёк к позднему cutoff. Результат сравнения фиксируется в `frozen-verified.json`.
3. После открытия записи скрипт проверяет начало входа через Яндекс и публикует `activation-authorized.json`. Эта квитанция разрешает запуск после перезагрузки. Фактическая политика `unless-stopped`, версия, readiness и конфигурация проверяются до записи итогового `accepted.json`. Запись и синхронизация этой квитанции с диском завершают переключение.
4. После принятия проверьте внешние HTTPS `/api/version` и `/api/ready`, сохранение сеанса и ключевые пользовательские сценарии выпуска. Проверка начала OAuth в скрипте заканчивается на корректном редиректе, полный вход проверяется через браузер. Зафиксируйте свойства нового контейнера, хеши копий и результаты проверки.

## Откат при сбое

До записи итогового `accepted.json` обычная ошибка или обработанный сигнал запускает откат. Он отзывает разрешение на запуск, останавливает контейнер кандидата, проверяет условия пина 29 и возвращает точный принятый образ `f100n26b`. Результат фиксируется в `rollback.json`. Изолированная копия и принятые квитанции предыдущего выпуска сохраняются. При работающей базе откат приложения оставляет текущие данные на месте.

При `rollback-incomplete.json`, потере питания или принудительном завершении отдельно сверяйте текущий контейнер, его image ID и policy, активные пины systemd и квитанции. Сохраняйте каталог попытки для диагностики. Повторное применение требует новой согласованной попытки. [Порядок работы с резервными копиями](../deploy/backup/README.md)
