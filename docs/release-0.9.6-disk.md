# Автоматическое восстановление выгрузки на Диск в 0.9.6

## Повторы

Таймер запускается в существующем процессе Next.js через корневой `instrumentation.ts` при Node.js runtime, в production, с `CANON_DISK_RECOVERY=true`, доступным режимом DynamoDB и настроенным Диском. Production Compose передаёт флаг с возможностью отключить таймер перед обслуживанием и приёмкой образа. Обычная и ручная выгрузка рабочего приложения сохраняет подтверждения независимо от флага. Для build, dev, статического экспорта и демонстраций таймер отключён. Запуск не блокирует готовность HTTP. Отдельный процесс, новый сервис и таблица не требуются.

Один таймер в процессе ставит следующий вызов после окончания предыдущего и не удерживает Node.js при завершении. Первый проход через 15 секунд, следующие через минуту. На проход максимум две последовательные операции и ограниченное AbortSignal чтение. В отдельные операции входят повтор передачи, подтверждение указателя, подготовка дерева и сверка сводки. Для передачи действует существующий 30-секундный предел, для её статуса — существующий предел записи. Медленная операция не создаёт очередь параллельных таймеров.

Очередь строится по текущим утверждённым карточкам и согласованным статьям. Повтор нужен для отсутствующего результата, `pending`, `failed`, несовпавшей редакции или устаревшей сводки папки. Активную попытку с `attemptId` пропускаем первые 90 секунд. Неудачные попытки повторяем не чаще чем раз в пять минут. Старейшие ожидающие записи идут первыми. Успешные актуальные файлы не выгружаются заново для формирования списка задач. Повтор использует наблюдаемую версию и действующие проверки `updatedAt`, `sourceRevisionId`, `attemptId` и версии реестра. Одновременный ручной запуск или второй процесс выигрывает либо получает условный конфликт; проигравший продолжит по актуальным данным в следующем проходе.

Старый утверждённый снимок карточки может оставаться действующим, пока редактируется новая заявка. Если у этого снимка уже есть выгрузка, она остаётся доступной. Если выгрузка прервалась до правки, для фонового повтора нужна отдельная цель `approvedSnapshot` с условием на сырой head и точную версию опубликованного снимка. На Диск идёт только снимок. Поля отклонённой или ожидающей заявки в экспорт не передаются. Эту ветку необходимо проверить отдельно с реальным YDB-префиксом.

## Прямой доступ с Диска

В каждом каталоге с материалами добавить папку `_Подтверждённые_сводки`. После атомарного подтверждения строки материала и реестра в DynamoDB записывается небольшой неизменяемый Markdown-файл с подтверждением. Имя начинается с номера подтверждения реестра фиксированной ширины, затем содержит ID подтверждения и хеш содержимого. Внутри — дата, номер, относительная ссылка на неизменяемую CSV и число строк, которые ещё ожидают выгрузки. Номер назначается при существующей условной транзакции как предшествующий номер плюс один. Запоздавшая запись старого Markdown не отменяет новый файл и не меняет их порядок. Одинаковый повтор пишет те же байты. Указатель на Диске не создаётся при незавершённой передаче CSV или неудачном условном обновлении реестра.

В актуальном реестре хранятся необязательные поля `sequence`, `pendingRows`, `receiptPath`, `receiptLastAttemptAt`, `receiptError` и `summaryInvalid`. После ошибки записи подтверждения обработчик восстанавливает его отдельно, без повторной передачи MD и CSV. Он резервирует попытку и отмечает результат с условием на тот же `versionId`. Для старого реестра без номера создаётся подтверждение с номером 0 после сверки состава папки, загрузки CSV с Диска и проверки SHA-256 по имени файла. Чтение проверяет до 8 МБ. Если файл отсутствует, недоступен для такой проверки или его сумма расходится, нужна новая сводка. Временная ошибка связи оставляет попытку в очереди.

При изменении состава создаётся новая сводка по действующему пути выгрузки. Один уже сохранённый материал даёт обновить сводку, пока другой материал ожидает повтора. После удаления последнего действующего материала обработчик пишет новую CSV с тем же заголовком и без строк, повторно проверяет отсутствие утверждённых материалов и подтверждает запись условной заменой реестра. Архив прежних документов остаётся на Диске.

Файл `_КАК_ЧИТАТЬ_РЕЗЕРВ.md` объясняет порядок. Откройте нужную папку, затем `_Подтверждённые_сводки`, выберите максимальный номер и перейдите по ссылке к CSV. В ней открывайте MD по записанному пути. Отметка «Ожидает выгрузки» говорит о неполном результате. Если этот материал нужен сразу, возьмите его последнюю полностью выгруженную редакцию из предыдущего подтверждения. Дата загрузки на Диск и время в имени CSV не определяют порядок. При недоступной базе доступна последняя подтверждённая копия, которую успели разместить.

## Дерево, совместимость и выпуск

При первой синхронизации подготовить стандартное дерево от общего паспорта до папок семи вузов, всех пяти подпапок каждого вуза и общего раздела совместных проектов. Папка `Готовые_статьи` появляется и в вузе без материалов. Подготовку выполнять для настроенного корня, с ограниченным параллелизмом, тем же дедлайном Диска и без повторов в уже успешно подготовленном процессе. Частично созданное дерево после ошибки достраивается безопасными повторными PUT каталогов. Совместные карточки и указатели используют текущую выгрузку.

Существующие 16 утверждённых и 11 ожидающих записей, восемь таблиц, версии, файлы MD, CSV и успешные пути сохраняются. Данные добавляются к действующим строкам реестра. Старый реестр читается без миграции. После первой новой записи нельзя возвращать 0.9.5 в режиме записи на этот префикс: он перезапишет реестр без номера и отметки размещения. Для паузы остановить операции записи и явно задать `CANON_DISK_RECOVERY=false`. Перед восстановлением зафиксировать состояние после выпуска и проверить старую копию в отдельном префиксе. До подключения восстановленной базы к Диску сверить её номера с уже размещёнными подтверждениями. Если номера разошлись, изолировать новый контур выгрузки по согласованной процедуре восстановления. Старый корень остаётся архивом.

Предлагаемые файлы реализации: корневой `instrumentation.ts`, `lib/disk-sync-service.ts`, `lib/disk-sync.ts`, `lib/models.ts`, `lib/yandex-disk.ts`, `deploy/compose.prod.yml`, `scripts/test-disk-recovery-096.ts`. При необходимости отделить запуск и выбор очереди в `lib/disk-recovery.ts`. Установка зависимостей не требуется.

## Приёмка

- Синтетическая проверка очереди подтверждает лимиты, паузу активной попытки, восстановление `failed`, отсутствие фоновой записи в демо и отсутствие повторов у актуальных документов.
- Подменённый транспорт роняет CSV и запись подтверждения отдельно. После автоматического повтора MD, CSV и подтверждение открываются по путям. Запоздавший старый ответ не становится выбранной сводкой. Сохранённый снимок карточки восстанавливается при ожидании заявки. После удаления последней карточки открывается пустая CSV, предыдущая редакция остаётся в архиве. Локальный mock без настроенного Диска проверяет, что таймер и внешние запросы не запускаются.
- `scripts/test-canon-disk-race.ts`, `test-durable-sync.ts` и `test-storage-sync.ts` проверяют совместимость текущих условий записи и старых путей.
- В изолированном согласованном корне проверить семь папок по пять подпапок, байты MD/CSV и имя подтверждения, ручной сценарий чтения при выключенном веб-приложении и повтор после рестарта. Проверка рабочих прав сотрудников выполняется владельцем действующего доступа по согласованному порядку.
