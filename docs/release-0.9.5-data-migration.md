# Данные и выпуск 0.9.5

План до изменения схемы. Добавочный протокол; существующие ID, публичные маршруты, статусы и шесть таблиц сохраняются. Новых постоянных хранилищ вне DynamoDB/YDB нет.

## Контракты

- `knowledge-card-versions`: PK `id`, одна неизменяемая утверждённая версия. Поля: `cardId`, точный снимок публичного содержания, версия/хеш содержания, автор и время фиксации, известные автор/время согласования, основание, источники, признак начального снимка с неизвестной прежней историей. Запись только `attribute_not_exists(id)`; изменение существующей версии запрещено. Публикация нового содержания и запись снимка выполняются одной поддерживаемой транзакцией. История не даёт дополнительного доступа к карточке.
- `workflow-records`: PK `id`, тип записи определяет серверную схему. Постоянные связи/решения: пакет инфоповода, разбирательство источников и проверка точной редакции. Общая очередь не копирует текущие карточки/документы/запросы; вычисляется из них и этих связей. Обновление по прочитанной версии, без last-write-wins.
- Карточка: необязательные метаданные ответственного и последней/следующей сверки, основание изменения и явные источники. Нет даты — срок не задан. Дата включительна по UTC. Просрочка не отменяет согласование и не скрывает факт. Назначение сверки использует границы текущего публичного снимка; назначенный сотрудник получает только право `verify` точной версии с If-Match, без прав на текст/план. Успешная сверка закрывает действующий план (`nextReviewAt` удаляется); следующую дату задают явно. Сверка не равна согласованию изменённого содержания.
- Редакторская редакция: необязательный список `{cardId, versionId}` с точными версиями источников. Старые `sourceCardIds` читаются, но не выдаются за зафиксированные версии. Проверка привязывается к `revisionId` и хешу точного текста. Изменение текста требует новой проверки. Согласование уже привязано к редакции и сохраняет этот контракт.
- Устаревание/задача: стабильный ключ материал/карточка/новая версия, вычисляемое состояние по использованным версиям и последней проверке. Повтор события не размножает задачи; новое подтверждённое сопоставление закрывает отставание. Автоматической перезаписи текста нет.
- Запрос: необязательные участники, ответственный и срок. Присоединение разрешено только уже имеющим право читать запись. Оно не расширяет видимость запроса, ответов или карточек. Нет автоматического объединения частных запросов и внешней рассылки.
- Пакет: ID участников, ответственный, срок, ссылки на утверждённые версии карточек и доступные документы/варианты. Каждое вложение повторно проверяется по его собственным правам. Разбирательство: два источника с объектом/годом/единицей/план-фактом, решение ответственного и история, без автоматического утверждения AI.

## Старые данные и повторяемость

У проектов добавлены явные «Не уточнено»/«не уточнён» для стадии/контура: такие записи не публикуются. Совместная инициатива может не иметь доказанного единственного инициатора. Необязательные `externalParticipantNames` позволяют честно назвать внешний вуз, не подставляя ID резидента: один резидент и внешний соавтор образуют совместную черновую карточку. Согласование внешней организации через реестр семи резидентов не имитируется; до отдельного подтверждения такой проект остаётся pending. Старые записи без этого поля сохраняют поведение.

Новые поля отсутствуют по умолчанию; чтение старых записей сохраняется. Существующие редакторские ревизии и карточки не переписываются задним числом. Начальный снимок текущего канона помечается как начало доступной истории, а не неизвестная историческая версия. Миграция создаёт недостающие таблицы; последующие backfill/import используют устойчивые ID, условия отсутствия/прочитанной версии и сохраняют чужие изменения. Согласования участников не фабрикуются. Черновые записи из публичных источников остаются pending при обязательном недостающем согласовании.

Гонка пользовательского типа закрывается условной версией типа (`updatedAt`), общей для записи карточки и изменения типа. Создание/удаление/правка custom-карточки валидирует прочитанную схему и в одной транзакции проверяет и обновляет эпоху типа. Изменение/удаление типа сначала читает эпоху, затем делает ConsistentRead Scan старых и новых карточек и завершает запись только при той же эпохе. Это учитывает legacy-карточки без счётчика и закрывает окно первой карточки. Перенос карточки в иной тип запрещён. Старый писатель не поддерживает протокол, поэтому одновременно его не запускать; отдельного backfill счётчиков нет.

Записи проверки материала содержат версию протокола пофразовой проверки. Прежний результат без этой версии считается устаревшим. Готовность проверяется по закреплённым снимкам и точному тексту; неизвестные формулировки остаются на ручной сверке. Явная ссылка в предложении проверяется именно по указанной карточке. Receipt ручной сверки публикации связан с `article.id`, её `approval.revisionId` и хешем текста, а не с оригиналом варианта или последующим приватным черновиком; в общей выдаче показывается только ссылка проверенной версии, без комментариев.

## Безопасный выпуск

1. Сохранить точный предыдущий SHA/образ, Compose и применимые несекретные настройки. Секреты остаются в существующем Lockbox/runtime-файле и не выводятся/не копируются в репозиторий или образ.
2. Получить согласованную полную копию всех таблиц Document API при остановленных записях. В архив включить схемы, данные, количества и контрольные суммы. Серверный файл root-only, без вывода содержимого. Не считать Markdown/CSV полной копией базы.
3. Проверить архив и восстановить в отдельную временную базу/изолированный набор таблиц. Цель должна быть пустой и явно выделенной; скрипт обязан отказываться от перезаписи существующих строк/таблиц. Сверить полный набор, ключи, количества и хеши, чтение/связи/права и тестовую запись. При неуспехе production не менять.
4. На копии/синтетике проверить повтор миграции/импорта и новые транзакции. Проверка DynamoDB Local не заменяет совместимость реально применяемых выражений YDB; выполнить небольшой тест в изолированных временных таблицах существующей YDB, если доступ позволяет, не затрагивая рабочие таблицы.
5. После обязательных тестов, независимого ревью и проверки финального Docker-образа выполнить добавочную миграцию штатным контейнерным процессом. Старый контейнер не должен писать во время миграции протокола и импорта. Пакет сначала dry-run; apply только прошедшие независимую сверку записи в допустимых статусах. Повтор не создаёт дублей и не перезаписывает существующие правки.
6. Проверить реальную выгрузку импортированных карточек в Markdown/CSV, а не только запись БД. При частичной ошибке доступна последняя полная версия, актуальная остаётся в очереди повтора. Результат устаревшей попытки не подтверждает новую редакцию. Общей транзакции БД и внешнего API нет.
7. Проверить HTTPS/0.9.5/health/ready, вход/роли, старые и новые сценарии, Flash в малом разрешённом наборе, Диск. Обновить документацию фактическим SHA, образом, количеством карточек и реальными результатами.

## Откат

До выпуска проверить запуск предыдущего образа с копией мигрированных данных. Добавочные таблицы и необязательные поля можно оставить при откате, но старый писатель способен обойти новый протокол: при его включении запись ограничить до решения о восстановлении. Не удалять историю и не выполнять обратную разрушающую миграцию. При необходимости восстановления сначала сохранить текущие данные, остановить запись и восстановить испытанную предрелизную копию в проверенную цель; явно зафиксировать временную границу и изменения после неё. Не перезаписывать рабочие данные вслепую. Критический сбой выпуска требует безопасно вернуть проверенный вариант.
