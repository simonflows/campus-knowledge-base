# Доступ и согласование в 0.9.6

## Маршруты

- Сотрудник PR создаёт и дополняет свой черновик до первого утверждения. Утверждённые сведения меняют назначенный руководитель или координатор. PR своего вуза оставляет комментарий на карточке, включая проект с участием своего вуза. Министерство и другие уполномоченные сотрудники могут направить запрос координатору через карточку либо назначенному владельцу.
- Совместный проект хранится в `02_Совместные_проекты`. Для каждого вуза-участника координатор назначает хотя бы одного руководителя из действующего каталога. Каждый вуз подтверждает редакцию отдельным действием через своего назначенного руководителя. При исключении вуза из опубликованного проекта участвует его ранее назначенный руководитель. Смена состава проекта с неназначенными прежними владельцами требует сначала назначить действующих ответственных.
- Министерство и АНО «РИОН» подтверждают общий паспорт и изменения параметров кампуса. ООО «ЧКК» подтверждает общую карточку паспорта, содержащую сведения об УНК, и карточки объектов с размещением в УНК. АНО «РИОН» подтверждает также межвузовские проекты и свои программы. Карточки ООО «ЧКК» об объектах и строительстве согласует его представитель. Координатор утверждает после требуемых подтверждений.
- АНО «РИОН» создаёт свои проекты и программы. Проект без вуза-инициатора помещается в папку проектов АНО «РИОН». ООО «ЧКК» создаёт карточки объектов и строительных параметров в разделе общих параметров. Связь с организацией устанавливает сервер по подтверждённой роли. Координатор назначает сотрудников этой организации владельцами по действующему каталогу. Эта связь сама по себе даёт только права на соответствующие карточки.
- Принятые запросы видны адресатам в «Моя работа». Если у карточки ещё нет назначенного владельца, запрос получает координатор с указанием фактического адресата в интерфейсе. История запросов остаётся в карточке.
- В конструкторе координатор может создать тип параметров ЧКК с неизменяемой отметкой `organizationScope: "chkk"`. У типа задаются обязательные поля для описания очереди, площади или тарифа. Карточки этого типа отделены от единого паспорта кампуса, находятся в подпапке «Параметры ЧКК» и требуют решения ЧКК и координатора. Сотрудник ЧКК выбирает только типы с этой отметкой, а сервер определяет зону ответственности по сохранённому типу. Переназначение отметки существующего типа возвращает ошибку, включая типы без карточек. Ранее созданные типы продолжают работать.

## Версия и хранение

- Действия подтверждения и утверждения используют `If-Match` с текущим `updatedAt`. Изменение между показом версии и действием приводит к ответу 409, включая конфликт внутри DynamoDB. Утверждение без версии возвращает 428. Отклонение старой карточки сохраняет совместимость с предыдущим API.
- В записи карточки добавляются необязательные поля `organizationScope`, `requiredApprovalStakeholderRoles`, `stakeholderApprovals` и `participantApprovalRecords`. У новых пользовательских карточек вузов сохраняется `universityId` из сессии. Запись подтверждения содержит идентификатор версии содержания, ID сотрудника и время. Изменение содержания сбрасывает одобрения. Изменение назначений в заявке также сбрасывает её одобрения. Участники новой редакции и требуемые участники предыдущей опубликованной редакции проверяются до утверждения.
- Существующие 16 утверждённых и 11 ожидающих карточек, включая записи с `ownerIds: []`, остаются в базе. Назначения и подтверждения для людей выполняются явно. Старые утверждённые снимки и их ссылки сохраняются. При новой правке прежний канон доступен до успешного согласования. Для уже ожидающих утверждения совместных проектов старые отметки без ответственного сотрудника не засчитываются.
- Руководитель сохраняет право редактировать созданный им старый пользовательский черновик без указанных учётных записей владельцев и отдельного поля вуза, если папка точно относится к его текущему вузу. Это право действует до появления утверждённого снимка или явного назначения.
- Поля живут в текущих записях DynamoDB. Дополнительной таблицы, индекса, перезаписи или миграции существующих записей нет. Защитные условия, атомарная запись версии и история утверждённых карточек остаются в существующей транзакции.
- Статья утверждается по той же редакции текста и по текущим опубликованным карточкам. Транзакция записи готовой статьи проверяет наблюдаемую версию каждой карточки и опубликованного снимка исходника. Меняется исходник до транзакции — публикация получает 409. До 22 источников помещаются вместе с тремя записями в лимит из 25 действий Document API. Черновики с большим списком сохраняются, перед утверждением список сокращают. Исторические редакции, источники готовых статей и файлы Диска сохраняются.

## Проверка и восстановление

Изолированная приёмка проверяет все семь вузов, чужую папку, подмену роли, подтверждение ответственным, утрату прежних подтверждений при редактировании, устаревший If-Match, маршруты трёх организаций, оба вида запросов на правку, доступ к предыдущему канону и блокировку статьи с устаревшим источником. Для проверок нужны синтетические учётные записи и данные. Реальные подтверждения в ходе приёмки не создаются.

Перед выпуском нужна проверенная резервная копия текущих таблиц и восстановление на отдельном префиксе. Обратный запуск старого интерфейса возможен с сохранением новых правил записи. Откат пишущего приложения до 0.9.5 требует остановки записи, сохранения состояния после выпуска и восстановления дорелизной копии с отдельной разборкой изменений, сделанных после неё. Резервные MD/CSV на Диске сохраняют историю содержания и дополняют копию базы.
