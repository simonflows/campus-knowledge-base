# Проверка Document API для выпуска 0.9.6

Проверку выполняют на точном образе кандидата до допуска записи в рабочем приложении. Скрипт [test-release-storage.ts](../scripts/test-release-storage.ts) создаёт восемь временных таблиц с новым префиксом, записывает в них только синтетические данные и возвращает один JSON-результат. Рабочие таблицы остаются вне разрешённого списка.

## Порядок

1. Выберите новый префикс вида `qa095-release096-<уникальный идентификатор>-`. Используйте только строчные латинские буквы, цифры и дефисы. Сохраните префикс для проверки образа после протокольного прогона. Этот формат сохраняет прежнюю проверку префикса.
2. На изолированном экземпляре для приёмки установите `CANON_DISK_RECOVERY=false`. В контейнере протокольного прогона установите те же ограничения. Скрипт отключает исходящий `fetch`, очищает настройки Диска и AI для своего процесса, создаёт временных сотрудников и подменяет проверку доступности хранилища на `DescribeTable` разрешённой таблицы. Он проверяет каждый элемент транзакции, включая `ConditionCheck`.
3. Запустите одноразовый контейнер точного образа со штатным закрытым файлом окружения. Значения файла в консоль и в отчёт не выводятся.

```sh
sudo -n docker run --rm \
  --env-file /run/campus/runtime.env \
  -e USE_DATABASE=true \
  -e CANON_DISK_RECOVERY=false \
  -e CAMPUS_RELEASE_STORAGE_TEST=yes \
  -e CAMPUS_RELEASE_QA_PREFIX="$QA_PREFIX" \
  --read-only --tmpfs /tmp:mode=1777 \
  "campus-kb:$CAMPUS_RELEASE_TAG" node --import tsx scripts/test-release-storage.ts
```

4. Проверьте `status` со значением `passed`, `mode` со значением `https-document-api`, восемь созданных таблиц и список пройденных проверок. Передайте только возвращённый `marker` в `CAMPUS_QA_MARKER` для уже подготовленного изолированного стенда образа. На том же префиксе проверьте `ready`, версию, SHA образа и чтение маркера через API. При ошибке сохраните имя этапа и тип ошибки из JSON. Рабочий выпуск требует последующего успешного прогона с новым префиксом.

## Что проверяется

- Миграция сохраняет старую строку. Новые версии карточек, согласования, события и метаданные Диска проходят существующие проверки условий записи.
- Обычная статья утверждается. Изменение карточки между чтением и транзакцией вызывает 409, сохраняя состояние статьи «На согласовании». Утверждённая версия под ожидающим редактированием остаётся доступна. 22 проверки источников и три записи проходят в одной транзакции. Известное противоречие в утверждённой карточке блокирует публикацию и без прямой ссылки на эту карточку в статье.
- Черновик и его редакция сохраняют сведения об опорном блоке согласованной публикации, включая редакцию, идентификаторы и заголовки. Если согласование публикации отозвали или время её обновления изменилось перед транзакцией, запрос возвращает 409. Черновик, его редакция и событие отсутствуют. Утверждение новой редакции с опорой на предыдущую редакцию той же публикации использует одно условное обновление публикации и укладывается в 25 операций с 22 карточками-источниками.
- Министерство, РИОН и ЧКК подтверждают только текущую редакцию паспорта. Попытки PR и утверждение без требуемых согласований отклоняются. Из двух запросов на одну исходную версию сохраняется один.
- Вложенный статус выгрузки меняет только утверждённый снимок. Старый ключ попытки не подтверждает указатель. Пустая сводка проходит условную замену реестра только с актуальным предшественником, а наличие материалов прекращает попытку до обращения к Диску.

## Границы проверки

На локальной DynamoDB префиксные таблицы проверяют формы команд и условия записи. Совместимость конкретной реализации YDB подтверждает только запуск на её Document API и чтение маркера точным образом. Этот прогон не проверяет живой транспорт Диска, доступ к папкам, реальный AI или поведение таймера. Для Диска нужна отдельная проверка в согласованном изолированном корне со сверкой байтов и открытием подтверждения при отключённом приложении.
