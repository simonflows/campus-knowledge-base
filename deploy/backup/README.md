# Резервное копирование «Канона»

«Канон» хранит данные в документных таблицах YDB Serverless. Яндекс описывает ежедневные управляемые копии для Serverless. Проверьте наличие свежих копий в консоли и оставьте включённым штатное расписание. Документация `ydb export s3` перечисляет строковые и колоночные таблицы, но не подтверждает выгрузку документных таблиц. YDB API позволяет работать с документными таблицами только на чтение. Совместимость выгрузки и обратного импорта с Document API требует отдельной проверки. [Копии Serverless](https://yandex.cloud/ru/docs/ydb/pricing/serverless), [документные таблицы](https://yandex.cloud/ru/docs/ydb/concepts/dynamodb-tables), [выгрузка YDB в S3](https://ydb.tech/docs/ru/reference/ydb-cli/export-import/export-s3)

## Проверка управляемой копии

1. В консоли Yandex Cloud откройте **Managed Service for YDB**, выберите каталог и исходную базу. В списке резервных копий сверьте исходную базу, время и статус последней завершённой копии. При необходимости получите список через `yc ydb backup list --folder-id "$BACKUP_FOLDER_ID"`. [Список копий](https://yandex.cloud/ru/docs/ydb/cli-ref/backup/list)
2. Создайте отдельную пустую Serverless БД для проверки, без подключения рабочего приложения. Выберите завершённую копию и запустите восстановление всех объектов в корень этой временной БД. Перед подтверждением сверьте ID целевой базы в форме восстановления. Если консоль не позволяет выбрать отдельную БД и нужный путь, остановитесь и проверьте параметры в документации `Database.Restore`. Дождитесь успешного завершения операции. [Создание Serverless БД](https://yandex.cloud/ru/docs/ydb/operations/manage-databases), [параметры восстановления](https://yandex.cloud/ru/docs/ydb/api-ref/Database/restore)
3. Проверьте восстановление до запуска миграции, чтобы она не создала пустые таблицы вместо отсутствующих. В изолированной среде доверенного оператора передайте `DOCUMENT_API_ENDPOINT` временной БД, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` отдельной учётной записи с правами на чтение схемы временной БД и `USE_DATABASE=true`. Передавайте ключи из менеджера секретов в окружение процесса. Из корня проверенной версии проекта с установленными зависимостями выполните `npm run check:deploy-storage`. Команда проверяет наличие всех ожидаемых таблиц, статус `ACTIVE` и схему первичных ключей. Любая ошибка требует разбора до продолжения. [Проверка таблиц](../../scripts/check-deploy-storage.ts), [ожидаемая схема](../../lib/schema.ts)
4. Сверьте полный перечень таблиц с исходным снимком, схемы и индексы, количество записей и контрольные суммы содержимого по каждой таблице. Для первого прогона используйте тестовую БД с известным набором записей и остановленной записью на время снятия контрольных значений и копии. Через Document API проверьте чтение карточек, черновиков, ревизий, доступов, согласований, аудита и очередей. Проверьте запись только во временной БД после сверки исходных данных, с отдельными правами на тестовую запись.
5. Зафиксируйте ID копии, время её создания, продолжительность восстановления и результаты сверки. Для пилота целевые значения из плана составляют до суток потерянных изменений и до четырёх часов на восстановление. Храните процедуру восстановления конфигурации, реестра сотрудников и доступа к секретам отдельно. [План проекта](../../plan.md#4-резервные-копии-и-облачный-ии)

## Допуск ежедневной копии в Object Storage

1. Уточните у Yandex Cloud, поддерживают ли `ydb export s3` и `ydb import s3` документные таблицы с сохранением их доступа через Document API. Для проверки подготовьте изолированные исходную и целевую Serverless БД, синтетические данные со всеми таблицами приложения и закрытый бакет. Отделите облачные учётные записи и права резервного копирования от учётной записи приложения. Для экспорта ограничьте запись выделенным бакетом или префиксом, для импорта выдайте отдельное право чтения. Передавайте S3-ключи из менеджера секретов только в окружение процесса как `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. [Аутентификация YDB CLI в S3](https://ydb.tech/docs/ru/reference/ydb-cli/export-import/auth-s3)
2. Если поддержка подтверждена, вручную выгрузите тестовую БД в новый префикс с меткой времени UTC и уникальным суффиксом. По ID операции через `ydb operation get` дождитесь `ready=true`, статуса `SUCCESS` и прогресса `Done`, затем проверьте наличие объектов выгрузки. Импортируйте тот же префикс в корень отдельной пустой Serverless БД, дождитесь такого же результата по ID импорта и выполните проверки таблиц, всех данных и операций Document API из предыдущего раздела. [Выгрузка](https://ydb.tech/docs/ru/reference/ydb-cli/export-import/export-s3), [загрузка](https://ydb.tech/docs/ru/reference/ydb-cli/export-import/import-s3)
3. Включайте ежедневный таймер только после успешного сквозного теста. При неподтверждённой совместимости подберите поддерживаемый способ копирования через Document API с сохранением схем, индексов и данных, затем повторите те же проверки восстановления. Для выбранного способа настройте оповещения об ошибке и отсутствии свежей завершённой копии. Версионирование и срок хранения настраиваются в бакете отдельно от задания выгрузки. Начальный ориентир плана для S3 — 14 ежедневных копий. [Версионирование бакета](https://yandex.cloud/ru/docs/storage/operations/buckets/versioning), [жизненный цикл объектов](https://yandex.cloud/ru/docs/storage/operations/buckets/lifecycles)
